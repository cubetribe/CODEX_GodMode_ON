# GodMode 3.0.0 — Lean Orchestration, Safe Migration

- Release date: 2026-08-10
- Release impact: major
- Core version: `3.0.0`
- GodMode installer minimum: Codex CLI `0.147.0`
- Optional GodMode Paperwork plugin: unchanged at `2.10.0`

## Executive summary

GodMode 3.0 rebuilds the core orchestration runtime around a simple premise:
strong parent models need clear authority, narrow boundaries, and observable
outcomes—not a mandatory committee. The release preserves worktree safety,
one-writer delivery, approval boundaries, recoverable installation, and
risk-based verification while removing duplicated roles, automatic companion
chains, and ceremonial gates.

GodMode 2.x encoded useful safeguards, but distributed them across 14 custom
agents, ten core skills, a 4,502-byte global prompt, a 4,824-byte workflow, a
six-thread base cap, mandatory Validator/Tester semantics, and a post-validation
Scribe phase. That structure was understandable when models needed more process
scaffolding. With GPT-5.6 Sol-class orchestration, much of it became persistent
context and coordination overhead rather than an independent safety boundary.

Version 3 keeps the rules that a model cannot safely infer from a task alone:

- which instructions have authority;
- who may write tracked files;
- when external actions require separate authority;
- how a named custom role is actually selected;
- which migration paths may remove old assets;
- what evidence proves the requested outcome.

Everything else is progressively disclosed through a selected skill, discovered
from the repository, handled by the parent, or checked by deterministic code.

## Why this is a major release

This is not a wording refresh. It changes the public orchestration contract,
the installed agent roster, the skill graph, the default concurrency policy,
the installer migration path, and the meaning of the validation roles.

Existing automation can break if it calls one of the seven retired agents,
expects `$godmode-departments`, assumes that Validator and Tester always run as
a pair, writes documentation after the final gate through Scribe, depends on
the bundled Playwright MCP entries, or reads the removed `agents.max_depth`
setting. The normal installer can retire exact known GodMode 2.0 assets, but it
will not guess how to transform modified copies.

The major version makes those compatibility boundaries explicit and gives
operators a recoverable migration instead of silently preserving a mixed 2.x
and 3.0 runtime.

## The design decision

The 3.0 work began with a critical audit of the installed GodMode system,
official OpenAI guidance, empirical context-file research, community reports,
and local behavior across stable and desktop Codex builds. The evidence did not
support keeping a large permanent team merely because more roles were
available.

The resulting design follows four rules:

1. **Start with the parent.** A clear task with no material uncertainty needs no
   custom specialist.
2. **Delegate a bounded unknown, not a phase name.** Use at most two specialists
   when independent investigation or isolation materially improves the result.
3. **Keep one tracked-file writer.** The parent or one built-in worker owns
   overlapping implementation scope; advisory specialists remain read-only.
4. **Prove outcomes with the narrowest valid gate.** Static consistency and
   executable behavior are separate concerns and are combined only when risk
   justifies both.

This is a reduction in standing machinery, not a reduction in rigor. In 3.0,
more rules are executable, fewer are repeated in every model context, and every
release-critical claim must still map to observed evidence.

## Measured package reduction

The table compares the unchanged 2.10 core inherited from GodMode 2.0 with the
3.0 core. Measurements use checked-in UTF-8 source bytes.

| Surface | 2.10 core | GodMode 3.0 | Change |
| --- | ---: | ---: | ---: |
| Custom agents | 14 | 7 | −50% |
| Agent-manifest source | 7,771 bytes | 3,400 bytes | −56.2% |
| Core skills | 10 | 9 | −10% |
| Core skill bodies | 20,245 bytes | 13,337 bytes | −34.1% |
| Global GodMode guidance | 4,502 bytes | 1,254 bytes | −72.1% |
| Core workflow skill | 4,824 bytes | 1,766 bytes | −63.4% |
| Public prompts | 9 / 22,727 bytes | 8 / 1,876 bytes | −91.7% by size |
| Packaged base concurrency cap | 6 | 2 | −66.7% |

These are source-size and inventory measurements, not tokenizer, quota,
latency, quality, or billing measurements. The package ships less instruction
source, while progressive disclosure determines what enters a particular run.
The figures do not prove a universal end-to-end token or cost reduction. Real
outcomes remain dependent on task, model, reasoning effort, tool use, and
delegation choices.

OpenAI's latest-model guidance reports directional internal improvements from
leaner prompts, but those figures are not measurements of this repository. The
architecture therefore treats lower consumption and equal-or-better task
quality as hypotheses to evaluate on representative workloads, not release
claims.

## New runtime contract

```text
applicable authority and repository law
                 ↓
goal + scope + observable done criteria
                 ↓
independent material uncertainty?
        no ──────────────→ parent works alone
        yes → 1..2 narrow specialists
                 ↓
parent or one built-in worker writes tracked files
                 ↓
static validator and/or executable tester, selected by risk
                 ↓
evidence for each done criterion + residual risk
```

The default is zero custom agents. Specialists never delegate again. A named
packaged specialist must be selected with the matching `agent_type`; using only
the same `task_name` creates a generic child and does not load the role
manifest. This detail is now both documented and checked because the live
release evaluation demonstrated that it is not safe to infer.

Commit, push, merge, release, deployment, credential use, and other external
mutations remain distinct authority boundaries. A green local check does not
grant permission for the next external action.

## Agent roster

Seven narrow custom specialists remain:

| Agent | Responsibility | Write boundary |
| --- | --- | --- |
| `api_guardian` | API, schema, CLI, config, and migration compatibility | read-only |
| `validator` | static syntax, structure, links, naming, and consistency | read-only |
| `tester` | build, execution, reproduction, and visible runtime behavior | disposable test output only |
| `runtime_platform` | OS, sandbox, runtime, and toolchain uncertainty | read-only |
| `workflow_design` | orchestration, skill, prompt, and handoff contracts | read-only |
| `docs_dx` | substantial public documentation and setup clarity | read-only |
| `ci_security_guardian` | CI permissions, action pins, trust, and secret boundaries | read-only |

The following 2.x roles are retired:

| Retired role | 3.0 owner |
| --- | --- |
| `researcher` | parent or built-in `explorer` |
| `architect` | parent, with a narrow domain specialist only when needed |
| `builder` | parent or one built-in `worker` |
| `scribe` | the single writer before final validation |
| `github_manager` | release skill plus repository governance |
| `workspace_governance` | repository `AGENTS.md` and deterministic preflight |
| `quality_operations` | scoped Validator/Tester evidence and CI |

The retirement removes generic permanent aliases without removing the work
itself. Discovery, design, implementation, release preparation, and quality
control still happen; they are simply owned by the most direct capable layer.

## Skills and primary modes

Four primary modes are now independent and mutually exclusive:

| Mode | Use |
| --- | --- |
| `$godmode-workflow` | non-trivial implementation or migration |
| `$godmode-debug` | reproduce, isolate, repair, and re-test a failure |
| `$godmode-review` | read-only findings-first assessment |
| `$godmode-prototype` | disposable local-only exploration |

Five support and stack skills load only when relevant:

- `greenfield-bootstrap`
- `release-manager`
- `apple-platforms`
- `web-platforms`
- `flutter-dart`

The removed `$godmode-departments` skill no longer inserts an organizational
layer between the task and a narrow specialist. Debug, review, prototype, and
workflow do not activate one another as mandatory companions.

## Validation architecture

GodMode 3 separates different kinds of evidence:

- `validator` answers whether static structure and contracts are internally
  consistent;
- `tester` answers whether executable behavior actually works;
- deterministic scripts own syntax, inventory, links, metadata, migration
  fixtures, version alignment, and other mechanically decidable rules;
- CI owns platform-specific and repository-wide release gates;
- capability diagnostics report workstation state but do not redefine package
  correctness.

Both agents are appropriate for mixed migrations, security-sensitive changes,
and major releases. They are no longer a mandatory pair for every Markdown or
single-surface change.

Documentation and release notes are written before final gates. This corrects
the old sequence in which Scribe could change the tracked diff after Validator
and Tester had already approved it.

The former aggregate environment check is now a small compatibility dispatcher:

- `check-static` validates deterministic package contracts;
- the Bash and PowerShell suites validate installation and migration;
- the isolated runtime test validates discovery and profile parsing in a
  temporary home;
- Paperwork retains its focused offline suite;
- `check-capabilities` diagnoses the current machine only.

## Configuration changes

The package remains model-neutral. It does not pin a model, reasoning effort,
provider, MCP server, plugin, or integration. GPT-5.6 Sol with Ultra reasoning
was used for demanding release evaluation, but choosing it is an operator
decision, not an installation side effect.

The portable base config now caps concurrency at two with the documented
`max_concurrent_threads_per_session = 2` field. Stable CLI `0.147.0` is the
supported floor because its GPT-5.6 Sol V2 spawn contract exposes `agent_type`.
In the tested `0.144.x` contract that field was absent: a matching `task_name`
created a generic Child and did not load the packaged manifest. Raising the
floor therefore protects the role sandbox and instructions, not merely config
syntax.

The undocumented `agents.max_depth` setting is removed. No-recursive specialist
delegation remains a prompt contract; GodMode does not claim that the config
technically sandboxes every possible nested call.

Bundled Playwright MCP entries and their managed output directory are removed
from the portable base. Browser tools and integrations remain user-owned and
can still be configured explicitly.

## Safe 2.x migration

The installer includes an explicit active/retired asset inventory and immutable
historical fixtures. Before writing package targets, a normal 3.0 upgrade
classifies every known retired path:

1. absent paths are ignored;
2. exact known 2.0 text, including CRLF-normalized content, is eligible;
3. modified files, links, wrong path types, and skill directories with unknown
   extra content fail closed with exit `5`;
4. eligible content is copied into a unique archive and verified;
5. only the verified legacy paths are removed from live discovery;
6. the seven current agents, nine skills, profiles, guidance, and inventory are
   installed;
7. an exact managed-asset check confirms the resulting state.

An exact rendered GodMode 2.0 base config is migrated only when it has no trust
entry or the sole generated trust entry matches the current `--repo` source. A
different trust entry or any other change makes the file user-owned and it is
preserved byte-for-byte. Model, effort, provider, plugin, MCP, project, and
integration choices are never merged speculatively.

Backups are stored outside live discovery:

```text
$CODEX_HOME/backups/install-archives/<timestamp-run-id>/
```

The installer completes all retirement conflict detection before creating
package targets or backup archives. Exit `5` therefore means the operator must
resolve the named legacy path before retrying; it does not describe a partial
3.0 installation.

## Paperwork remains independent

GodMode 3.0 changes the core orchestration runtime only. GodMode Paperwork
remains an optional, separately installed plugin at version `2.10.0`. The core
installer neither installs nor activates it, and existing Paperwork 2.10 cases
require no 3.0 migration.

This repository now expresses that separation explicitly:

- root `VERSION` tracks the GodMode core distribution;
- `plugins/godmode-paperwork/VERSION` tracks the plugin package;
- the plugin manifest must match the plugin-local version;
- the persisted Paperwork evidence and validator contracts remain `2.10.0`.

The plugin is not bumped merely to mirror a core release. Its engine version is
stored in cases, validations, receipts, and archives; changing it without a
backward-compatibility design would invalidate existing evidence. A future
Paperwork release must define and test that migration separately.

## Breaking changes

- Seven custom agents are removed: `researcher`, `architect`, `builder`,
  `scribe`, `github_manager`, `workspace_governance`, and
  `quality_operations`.
- `$godmode-departments`, the department guide, department/report templates,
  and the historical improvement-sprint prompt are removed.
- Validator and Tester are no longer mandatory double gates for every task.
- The post-gate Scribe phase is removed; documentation is part of the normal
  writer's scope before final validation.
- `agents.max_depth` is removed from packaged config.
- Bundled Playwright MCP configuration and the managed Playwright output path
  are removed.
- The minimum supported Codex CLI increases to `0.147.0`.
- Automation that references retired roles, companion mode chains, six-way
  default concurrency, or old gate semantics must be updated.
- Exact known legacy assets are recoverably retired during normal installation;
  modified or structurally unknown copies require manual resolution.

## Upgrade

Check out the immutable release and run the normal installer. Do not use reset
flags for a routine upgrade.

macOS or Linux:

```bash
git fetch origin --tags
git checkout v3.0.0
./scripts/apply-global-codex-setup.sh
./scripts/apply-global-codex-setup.sh --check
```

Windows PowerShell:

```powershell
git fetch origin --tags
git checkout v3.0.0
.\scripts\apply-global-codex-setup.ps1
.\scripts\apply-global-codex-setup.ps1 -Check
```

Then start a fresh Codex task so global guidance, profiles, agents, and skills
are rediscovered.

If the installer exits `5`, preserve the named path and inspect how it differs
from the known 2.0 fixture. Rename or migrate user-owned content deliberately,
then rerun the installer. Do not delete a conflicting path merely to satisfy the
check.

Use `--reset-config` only when replacing user-owned configuration is intended.
Use `--reset-agents` only when replacing the complete global AGENTS file is
intended. Both are broader authority boundaries than a normal upgrade.

## Rollback and recovery

Before installation, retain the existing repository/tag and note the active
Codex home. The installer already makes per-run backups for managed replacement
and retirement paths.

To recover one archived file:

1. stop active Codex tasks;
2. locate the applicable archive under
   `$CODEX_HOME/backups/install-archives/`;
3. verify the archived item and original target;
4. copy it back deliberately;
5. start a fresh task.

Restoring one retired 2.0 asset into an otherwise 3.0 installation intentionally
makes the 3.0 `--check` fail. A complete rollback must restore a coherent older
runtime from an older release, not mix isolated assets across versions.

After the Git tag and GitHub Release are published, `v3.0.0` is immutable. A
release defect is corrected with a new patch version; the tag must never be
moved or force-replaced.

## Release verification

The final release is gated on the exact tracked state, not an earlier candidate.
The release pipeline covers:

| Gate | Coverage |
| --- | --- |
| deterministic static contract | TOML, JSON, links, roster, inventory, prompt budgets, release state, and plugin metadata |
| Bash installer suite | 17 fresh-install, preservation, migration, conflict, backup, drift, and idempotence groups |
| Windows installer matrix | 15 groups under Windows PowerShell 5.1 and the same 15 under PowerShell 7 |
| isolated runtime | clean temporary homes, discovery, retired-skill rejection, and profile parsing against tested CLIs |
| Paperwork | plugin validation, Python compilation, and 59 offline unit tests |
| routing | five deterministic mode and specialist-budget fixtures |
| live orchestration | Sol/Ultra zero-specialist routing plus explicit Validator/Tester role binding in synthetic, credential-isolated fixtures |
| CI hygiene | ShellCheck, actionlint, Markdownlint, and CodeQL |
| publication | protected-main squash, post-merge checks on the exact SHA, annotated tag, and verified GitHub Release |

The live harness is deliberately fail-closed. A model's final `PASS` string is
not sufficient. Stable CLI `0.147.0` traces are verified from the persistent
parent/child session graph and Child rollout as well as the public trace.
Multi-agent traces are not run with `--ephemeral`, because the CLI needs a
registered parent thread to materialize children reliably.

The decisive stable-floor trace ran with Codex CLI `0.147.0`,
`gpt-5.6-sol`, and Ultra reasoning. The persisted Parent calls contained
`agent_type=validator` and `agent_type=tester`; the Child metadata reported the
matching non-null roles; both role manifests appeared in the Child developer
instructions; `cmp -s contract.json contract.expected` and `./probe.sh` each
exited `0`; and the synthetic Git fixture remained clean. A separate
zero-specialist Sol/Ultra trace created no Child. This is the evidence boundary
behind the 0.147.0 installer floor.

The final command results and exact GitHub workflow status are recorded in the
release pull request and the published GitHub Release. Any tracked edit after a
gate invalidates affected evidence and requires that gate to run again.

## Security and privacy boundaries

The release does not add credentials, service endpoints, model pins, or silent
network integrations. Test credentials used for live Codex evaluation stay in
a permission-restricted temporary Codex home and are removed after evaluation.
Synthetic live fixtures contain no repository secrets or personal documents.

Paperwork remains local-first and explicit. It performs no cloud OCR, document
upload, silent dependency installation, form submission, original deletion, or
professional certification. Paperwork cases and exports must remain outside Git
worktrees and plugin caches.

## Known limitations

- Source reduction is not proof of lower real-world token use, lower cost, or
  equal-or-higher quality.
- Sol and Ultra availability, latency, and quota behavior vary by account and
  task.
- Named-role routing depends on the Codex spawn contract; the installer rejects
  `0.144.x`, where GPT-5.6 Sol can omit `agent_type` and silently start a generic
  Child instead.
- Prompt rules prohibit recursive specialist delegation, but the package does
  not claim a config-enforced depth sandbox.
- Public JSONL output is not the sole evidence for delegated Child execution;
  persistent session artifacts are required for the complete release audit.
- Optional installed apps or plugin catalogs can still be discovered by Codex
  product infrastructure. The live release fixture disables their use and
  restricts workspace input, but does not claim that local product caches are
  absent.
- Paperwork remains version `2.10.0` and retains its documented Unix-like
  runtime boundary.
